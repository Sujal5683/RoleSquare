     3→# Workspace Intelligence Platform — Complete SaaS Architecture \& Build Blueprint
     4→
     5→Workspace Intelligence Platform (WIP) is architected as a backend-first, multi-tenant, AI-native SaaS that turns Gmail/Drive/Docs/Sheets/Forms content into structured, governed, queryable datasets through an asynchronous, evidence-backed extraction pipeline. Below is the full production blueprint covering product, architecture, schema, APIs, UI, security, and rollout — built on your specified stack (React 19/NestJS/Supabase Postgres/pgvector/BullMQ/Redis/Gemini).
     6→
     7→## Core Product Model
     8→
     9→The entire platform reduces to one composable pipeline abstraction, which keeps every other system (jobs, permissions, AI) simple and uniform.
    10→
    11→```
    12→SOURCE (Gmail rules) + SCHEMA (fields) + POLICY (schedule/validation)
    13→   = PIPELINE → produces → DATASET (rows with evidence-backed values)
    14→```
    15→
    16→Two hard architectural boundaries must exist from day one:
    17→
    18→- **Data Acquisition Layer**: Google → your system (OAuth, Gmail sync, Drive discovery, document parsing) — pure ingestion, no intelligence.
    19→- **Intelligence Layer**: your database → AI → structured, validated, evidence-linked records — this is where extraction, RAG, and agents operate.
    20→
    21→Because Gmail (`gmail.readonly`) and broad Drive scopes are classified by Google as **restricted scopes**, any public app storing/transmitting this data must pass Google's security assessment and CASA verification, and should request the narrowest scopes needed per feature rather than one broad grant at signup.[^1_1]

    40→                     ┌──────┴──────┐

    44→
    45→NestJS modules map 1:1 to domains: `auth`, `organizations`, `google-connections`, `sources`, `gmail-engine`, `drive-engine`, `document-processing`, `ai-extraction`, `rag`, `datasets`, `sharing`, `jobs`, `audit`, `observability`. Every module exposes a service + controller + repository, and all writes go through a service layer that emits audit events — controllers never touch Supabase directly.

    47→## Authentication \& Multi-Tenancy
    48→
    49→| Layer | Entity | Notes |
    50→| :-- | :-- | :-- |
    51→| Identity | `users` | Supabase Auth (Google OAuth sign-in) |
    52→| Google account | `google_connections` | Separate from app identity; supports multiple accounts per user, token refresh, scope tracking |
    53→| Tenant | `organizations` | Owner/Admin/Manager/Member/Viewer roles |
    54→| Membership | `organization_members` | Role + status (invited/active/removed) |
    55→| Access | RLS policies keyed on `organization_id` | Enforced at DB, not app code |
    56→
    57→The tenancy boundary must be enforced in Postgres, not application logic — every tenant-scoped table gets a non-nullable, indexed `organization_id`, RLS is enabled with explicit deny-by-default policies, and membership checks use a `SECURITY DEFINER STABLE` helper function to avoid the classic self-referencing RLS recursion trap. Clients always use the Supabase anon key + user JWT; the `service_role` key is confined to backend workers only, never exposed to the browser.[^1_2][^1_3][^1_4][^1_5]
    58→
    59→```sql
    60→create policy org_isolation_select on datasets
    61→for select to authenticated
    62→using (organization_id = ANY (private.user_org_ids()));
    63→
    64→create policy org_isolation_write on datasets
    65→for insert to authenticated
    66→with check (organization_id = ANY (private.user_org_ids())
    67→            and private.user_role(organization_id) in ('owner','admin','manager'));
    68→```

   124→
   125→Every table above needs `organization_id`/derivable-tenant FKs, composite indexes on `(organization_id, created_at)`, and RLS enabled with `FORCE ROW LEVEL SECURITY`. `document_embeddings.embedding` uses `pgvector` with an HNSW or IVFFlat index for similarity search.[^1_3]
   126→
   127→## Gmail Sync \& Job Pipeline
   128→
   129→Gmail push notifications require a `users.watch()` call against a Pub/Sub topic, but the watch **expires after 7 days with no error on lapse** — the system must re-issue `watch()` on a daily cron well before expiry and self-heal via `history.list()` reconciliation to avoid silent sync gaps. Every scan is a queued job, never a synchronous request:[^1_6][^1_7]
   130→
   131→```
   132→POST /sources/:id/scan → create ai_job (GMAIL_SCAN) → BullMQ queue → worker
   133→  → batch fetch → rule match → store email → discover attachments/links
   134→  → queue DRIVE_DISCOVERY / DOCUMENT_PARSE → AI_EXTRACTION → VALIDATION → dataset write
   135→```
   136→
   137→Job types: `GMAIL_SCAN, EMAIL_PARSE, ATTACHMENT_PROCESS, DRIVE_DISCOVERY, DRIVE_INDEX, DOCUMENT_PARSE, AI_EXTRACTION, AI_VALIDATION, EXPORT` — each with retries, exponential backoff, and a dead-letter queue, with per-stage progress exposed to the frontend (e.g., "3 attachments found → 2 Drive files discovered → AI extraction ⟳").
   138→
   139→## AI Extraction \& Evidence Rule
   140→
   141→Every `dataset_values` row is generated by the Extractor agent from a resource bundle (email + attachments + linked Drive/Docs/Forms treated as one context) and must never be stored without: value, confidence score, evidence snippet, source file, page/chunk reference, and timestamp — this evidence trail is what makes the platform auditable rather than a black-box AI tool. The six agents (Extractor, Analyst, Validator, Transformer, Researcher, Assistant) share a common orchestration layer with Gemini as primary model and a defined multi-model fallback chain for rate-limit/outage resilience, consistent with your existing fallback architecture work.

   193→# Workspace Intelligence Platform
   194→
   195→## Complete Product Requirements and Production Architecture Document
   196→
   197→Workspace Intelligence Platform is a production-grade, multi-tenant, AI-powered SaaS platform that connects to Google Workspace accounts and converts emails, attachments, Drive resources, Docs, Sheets, Forms, and linked content into structured, searchable, collaborative datasets. The platform is designed as a backend-first system in which all ingestion, synchronization, parsing, AI extraction, validation, indexing, and sharing workflows run server-side through asynchronous pipelines. Gmail push notifications require periodic renewal because Gmail API watch subscriptions expire after seven days, so the sync engine must include watch renewal and reconciliation logic to prevent silent sync gaps.[^2_1]
   198→
   199→## Product Vision
   200→
   201→The product enables individuals, teams, and organizations to connect one or more Google accounts, define intelligent ingestion rules, discover relevant resources from Gmail and Google Drive, process content and attachments, extract structured fields through AI, validate outputs with evidence, and publish the results into collaborative datasets. The platform acts as a system of structured intelligence on top of Google Workspace rather than a simple inbox automation layer. Google Workspace integrations involving Gmail and broad Drive access use sensitive or restricted scopes, so the OAuth experience, scope strategy, and launch checklist must be designed around Google's verification and security assessment requirements.[^2_2]
   202→
   203→## Product Goals
   204→
   205→- Convert unstructured Google Workspace content into structured operational data.
   206→- Support individuals, departments, and organizations with strict multi-tenant isolation.
   207→- Provide evidence-backed AI extraction with confidence, source references, and auditability.
   208→- Enable large-scale background processing for millions of emails and documents.
   209→- Deliver enterprise-ready permissions, observability, compliance controls, and security.
   210→- Support flexible schemas, AI workflows, dataset exploration, and sharing.
   211→
   212→
   213→## Non-Goals
   214→
   215→- The frontend is not a primary processing engine.
   216→- The product does not rely on browser-side parsing of emails or documents.
   217→- The platform is not a generic no-code automation builder in v1.
   218→- The platform is not limited to one Google account per user.
   219→- The system does not store AI-extracted values without evidence.

  1208→## RLS Architecture
  1209→
  1210→Supabase multi-tenant security should be enforced primarily with Row Level Security at the database layer, using tenant-scoped policies and helper functions rather than depending on application filters alone.[^2_5][^2_6][^2_4]
  1211→
  1212→### RLS Principles
  1213→
  1214→- Enable RLS on every tenant-facing table.
  1215→- Deny by default.
  1216→- Scope reads and writes to organization membership.
  1217→- Use helper SQL functions for role checks.
  1218→- Keep `service_role` server-side only; never expose it to the browser.[^2_7][^2_8]
  1219→- Test RLS with automated policy tests.
  1220→
  1221→
  1222→### Example Policy Model
  1223→
  1224→- Users can read organizations where they are active members.
  1225→- Users can read datasets only for organizations they belong to.
  1226→- Only owner/admin/manager can mutate sources and schemas.
  1227→- Dataset values inherit dataset-level and field-level access rules.
  1228→- Sharing overlays can only expand access through approved and logged grants.
  1229→
  1230→
  1231→### Helper Functions
  1232→
  1233→- `private.user_org_ids()`
  1234→- `private.user_role(org_id uuid)`
  1235→- `private.is_org_member(org_id uuid)`
  1236→- `private.can_manage_org(org_id uuid)`
  1237→- `private.can_edit_dataset(dataset_id uuid)`
  1238→
  1239→Using stable helper functions also avoids recursive policy patterns that commonly cause poor performance or broken access control in Supabase multi-tenant deployments.[^2_4][^2_5]
  1240→
  1241→## Security Architecture
  1242→
  1243→### Security Requirements
  1244→
  1245→- Encrypt Google tokens at rest.
  1246→- Use server-side secret management.
  1247→- Restrict service role key to backend workers.
  1248→- Enforce RLS everywhere.
  1249→- Apply per-route permission guards in NestJS.
  1250→- Implement rate limiting at API and job submission layers.
  1251→- Log all privileged actions.
  1252→- Validate and sanitize AI inputs.
  1253→- Prevent prompt injection through source separation and instruction hardening.
  1254→- Isolate tenants in storage paths and DB access.
  1255→
  1256→
  1257→### Threat Model
  1258→
  1259→Threats addressed:
  1260→
  1261→- Unauthorized account access
  1262→- Cross-tenant data leakage
  1263→- Token theft
  1264→- Prompt injection from email/document content
  1265→- Malicious file uploads
  1266→- Queue abuse
  1267→- Replay attacks on webhooks
  1268→- Privilege escalation
  1269→- Excessive AI cost amplification
  1270→

  1272→### Google OAuth and Scope Strategy
  1273→
  1274→Google API restricted scopes require formal verification and, for applicable apps, external security assessment before production launch, so the product should separate minimum onboarding scopes from advanced optional scopes and explain scope purpose clearly during consent.[^2_2]
  1275→
  1276→Recommended scope tiers:
  1277→
  1278→- Authentication scopes
  1279→- Minimal Gmail read scopes for source use cases
  1280→- Drive metadata scopes where possible first
  1281→- Expanded content scopes only when feature requires them
  1282→
  1283→
  1284→### Token Handling
  1285→
  1286→- Encrypt tokens before persistence.
  1287→- Rotate encryption keys through managed secret/KMS strategy.
  1288→- Track token refresh success/failure.
  1289→- Mark connections degraded before expiration if refresh fails.

  1294→### Model Strategy

  1297→- Secondary fallback: configurable provider chain

  1304→### AI Workflow
  1305→
  1306→1. Build resource bundle.
  1307→2. Retrieve relevant chunks if needed.
  1308→3. Build schema-aware prompt.
  1309→4. Execute extraction.
  1310→5. Parse strict JSON.
  1311→6. Validate output.
  1312→7. Write extracted fields with evidence.

  1316→

  1318→- Content marked as untrusted source material.
  1319→- Reject unsupported fields or fabricated values.
  1320→- Require evidence for every extracted value.
  1321→- Score low evidence density as low confidence.

  1849→## Final Architecture Recommendations
  1850→
  1851→- Use Supabase as the primary database, auth, storage, and Postgres platform, but keep NestJS as the true application backend orchestration layer.
  1852→- Keep all processing asynchronous and server-side.
  1853→- Treat Gmail, Drive, and document content as untrusted input.
  1854→- Make evidence mandatory for all extracted values.
  1855→- Push tenant isolation into PostgreSQL with RLS and helper functions rather than relying only on app-layer filters.[^2_6][^2_5][^2_4]
  1856→- Design Google scope requests in phases to reduce verification risk and improve user trust.[^2_2]
  1857→- Build renew-and-reconcile logic into Gmail push integration from day one because watch subscriptions expire automatically.[^2_1][^2_3]
